# CIndRA product assembly

Build review-ready reports from products generated by the repository's approved workflows. Treat figures, tables, metrics, site configuration, and source records as inputs; report files are assemblies, not sources of record.

Use the relevant domain skill to interpret each product. Read `../output-conventions/SKILL.md` when locating or naming outputs and `../data-sources/SKILL.md` when writing source attribution. If an expected artifact is absent, label it missing or deferred; do not fabricate it or run a materially new analysis unless the user also requests that work.

## Establish scope

Record before assembly:

- report title, requested format and language;
- profile: `National` or `Regional`;
- site/country/EEZ or regional scope;
- included indicator families;
- analysis and reference periods actually used;
- generation date and repository version/commit when available;
- package status: `Draft`, `Scientist-reviewed`, `Approved for report use`, `Experimental`, `Deferred`, or `Optional`.

Default new assemblies to `Draft`. Only a human scientific reviewer may assign `Scientist-reviewed` or `Approved for report use`.

## Phase A — Inventory

Inspect the applicable output directories and build `product_inventory.csv` (or an equivalent table in the report) with:

- `product_id`, stable within the package;
- indicator family and National/Regional profile;
- role: primary, supporting, diagnostic, optional, deferred, or missing;
- output path and type;
- site, station, source, EEZ or regional scope;
- analysis/reference period and units;
- source dataset and method/notebook/function reference;
- caption, provenance, validation and review status;
- issue-log reference.

Never hide missing expected products. Do not assume that similarly numbered figures in different domain folders are the same product.

## Phase B — Captions

Every displayed figure and table needs a caption that identifies:

- product ID, indicator and spatial scope;
- analysis period and reference period where relevant;
- source/station identifiers and dataset version where available;
- units and the statistic, threshold or category shown;
- selection, aggregation and trend method needed for interpretation;
- QC/completeness status and important limitations;
- review status when the product is not approved.

Keep captions factual. Do not infer causation from trends or ENSO group differences.

## Phase C — Methods and limitations

For each indicator family, summarize the actual repository path used: configuration, cached input, notebook, helper functions, thresholds, temporal aggregation, spatial selection, trend units and persistence path. Include only methods evidenced by code, metadata or generated artifacts.

Report limitations that materially affect interpretation, including incomplete records, station representativeness, gridded-versus-point differences, interpolation or estimated values, unresolved QC, provisional final years, missing regional capability and exploratory outputs.

## Phase D — Provenance

Create `provenance.json` or a clearly structured equivalent. For every primary product or narrative claim, preserve when available:

- output path and product ID;
- dataset, provider, URL/path, version and access date;
- station/source ID, variables, native resolution and units;
- site/EEZ/region selection and aggregation method;
- analysis/reference period, parameters and thresholds;
- notebook, helper/function, repository commit and run timestamp;
- validation and review status.

Machine-readable CSV/JSON files and repository outputs remain authoritative. Do not present the report document as the source of record.

## Phase E — Validation and issue log

Check that files exist and are readable, figures have captions, units and periods agree across figure/table/text, cited sources match the domain skill, and narrative values can be traced to a table/JSON or computed output. Record failures in `issue_log.csv` with `issue_id`, `product_id`, severity, status, description, blocking status, recommended action and affected outputs.

Use these cross-domain checks:

- National rainfall and air temperature resolve the saved GHCN site configuration and disclose the completeness filter and 1961–1990 baseline where used.
- Rainfall units distinguish mm/day, mm/year, days/year and rates per decade.
- Temperature units distinguish °C, °C/decade, days/year and percentile/base-period definitions.
- SST states NOAA OISST product/resolution, °C or °C/decade, EEZ mask or Pacific extent, and climatology/anomaly period.
- Tropical-cyclone products state radius, box-entry or genesis selection; wind thresholds; missing-wind treatment; count/ACE units; and whether the final year is complete.
- Tide-gauge sea level is relative; altimetry is absolute. Combined displays do not imply the quantities were merged. State datum, mm/yr or cm, and flood threshold/time convention where applicable.
- Regional sea level remains unavailable unless a real workflow has been added; never turn the placeholder or experimental helpers into a reported result.

## Phase F — Report assembly

Unless the user specifies another structure, assemble:

1. Cover/title block: package ID, scope, date and review status.
2. Executive summary containing only traceable findings and a compact metrics table.
3. Data coverage and product inventory.
4. One section per indicator family: key products, captions and concise interpretation.
5. Methods.
6. Limitations and data gaps.
7. Sources and provenance summary.
8. Validation status and unresolved issues.
9. Reproducibility references and appendix/backbone-file index.

Prefer `report_section/structured_product_section.md` as the editable canonical assembly. Produce DOCX or PDF only when requested and supported by available document tools. Preserve figure aspect ratios and readable captions; never stretch figures to fill a page.

Recommended package:

```text
report_section/
|-- structured_product_section.md
|-- structured_product_section.docx   # optional/requested
|-- structured_product_section.pdf    # optional/requested
|-- product_inventory.csv
|-- provenance.json
|-- validation_checklist.csv
`-- issue_log.csv
```

Do not automatically copy notebooks, raw data or the repository into the report package. Furnish an annotated notebook, environment file or product-to-code crosswalk only when explicitly requested; otherwise include concise repository/notebook/function references.

## Final checks

- Scope, periods, units, data sources and status are explicit.
- Every figure/table is inventoried and captioned.
- Every quantitative claim is traceable to an artifact.
- Missing, optional, diagnostic and deferred products are visible.
- Methods do not exceed what the repository implements.
- Limitations, validation failures and unresolved issues are not softened or omitted.
- Draft material is not represented as scientist-reviewed or approved.
